Supabase October 30 change: new tables need grants

On October 30, 2026 Supabase applies a new default to all existing projects: tables you create in the public schema are no longer reachable through the Data API until you grant access. Existing tables keep their current grants. New projects have used this behavior by default since May 30, 2026, and it covers both the REST and GraphQL Data APIs. The risk is not the change itself. It is the quick fix people (and AI coding tools) will reach for when the app starts throwing errors.

Verified October 20, 2026. Source: Supabase changelog, "Tables not exposed to Data and GraphQL API automatically".

What you will see

After the change reaches your project, a new table created by a migration, a CLI script or an AI agent returns an error through supabase-js or /rest/v1/ instead of data:

{ "code": "42501", "message": "permission denied for table your_table" }

The response also includes a hint with the exact GRANT for the missing role and privilege. Apps that only talk to Postgres over a direct connection (psql, an ORM or a server with a connection string) are not affected.

The unsafe fix

The fastest way to make the error go away is to grant everything to everyone and move on:

grant select, insert, update, delete on public.your_table to anon, authenticated;

If that table has no Row Level Security, you have just made it readable and writable by anyone holding your public anon key. Grants decide whether a role can reach a table at all. RLS decides which rows it sees. You need both.

The safe fix, as one unit

  1. Grant only the role and actions you need. Most app tables need authenticated, not anon. Read-only public data needs select only. If server code uses the service_role key against the Data API, grant that role too (Supabase's own example does).
  2. Enable RLS in the same migration. alter table public.your_table enable row level security;
  3. Add owner policies. For example using (auth.uid() = user_id) for SELECT, UPDATE and DELETE, and with check (auth.uid() = user_id) for INSERT and UPDATE. A policy of just auth.uid() is not null lets every signed-in user read every row.
  4. Tell your AI tool. Supabase recommends updating its system prompt or using the Supabase agent skill. Add a line to your rules file (Cursor rules, CLAUDE.md and similar): "Every new public table gets explicit grants, RLS enabled and owner policies in the same migration."
  5. Test as the anon key and as two users. Run the free Supabase check for the anon key, then sign in as user B and try to read user A's rows by id. See the RLS checklist.

Before October 30

Until then, Supabase says Security Advisor flags affected tables with the fix SQL, and owners and admins of active projects get a final notice email on October 23. You can also opt in early on an existing project (see the changelog for the SQL). Use the time to add explicit grants to your migration templates, so the next table your AI agent creates works on day one without anyone reaching for a blanket grant.
